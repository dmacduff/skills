# Scaffold Ansible Env

Stand up a reproducible Ansible **environment** in the current directory: uv
owns Python, one authoritative lockfile with two derived exports, pre-commit
enforces hygiene, and the execution-environment question gets a decision, not
a shrug.

Environment only. Project structure — `ansible.cfg`, `inventory/`, `roles/`,
playbooks — belongs to a broader scaffold that calls this one. Existing
Ansible content in the directory is read-only input: mine it for dependencies
and rubric evidence, and leave every byte of it alone.

The environment is the source of truth for tool invocations: before running
any command sketched below, confirm its flags against the tool's `--help`.
Versions drift; this file does not chase them.

## Steps

### 1. Survey

Establish, from the directory and the user's request:

- Greenfield or retrofit (existing playbooks/roles/`requirements.yml`)?
- Which collections the project needs, and whether any require system-level
  dependencies (compilers, `libssh`, vendor SDKs).
- Whether Python source (modules, filter plugins) exists or is planned. Ruff
  ships by default; leave it out only when the user signals the project will
  never contain Python.

### 2. Python environment

uv owns the interpreter and the venv:

- `uv init --bare` (skip if `pyproject.toml` exists), then `uv python pin` a
  current supported Python.
- `uv add ansible-core` — plus any Python libraries the project's collections
  document as requirements.
- `uv add --dev ansible-lint yamllint pre-commit ruff` (ruff per step 1).

### 3. Lock artifacts

`uv.lock` is primary and authoritative. Export the two derived artifacts,
runtime dependencies only — the stock box and the EE run playbooks, they
don't lint them; `uv sync` is what reproduces the full dev environment:

- `uv export --no-dev --format requirements.txt -o requirements.txt`
- `uv export --no-dev --format pylock.toml -o pylock.toml`

Keep uv's autogenerated headers — they mark the files as derived. Both files
are regenerated from `uv.lock`, never hand-edited; the generated README says
so (step 7).

### 4. Galaxy manifest

Write `requirements.yml` listing the collections from step 1, or an
empty-but-valid manifest (`collections: []`) when there are none yet. Together
with `requirements.txt`, this is exactly what `ansible-builder` consumes — the
output is EE-ready whether or not step 6 builds one.

### 5. Hygiene

- `.pre-commit-config.yaml` from the roster below.
- `.yamllint` extending the default config, relaxing only the rules that
  fight ansible-lint's formatting opinions (line length, comment indentation).
- `.gitignore` covering `.venv/` and, if step 6 fires, the EE build context.
- `uv run pre-commit install`, then `uv run pre-commit run --all-files`.

**Done when the full-tree pre-commit run passes.** Fix findings in files this
skill created; report findings in pre-existing files to the user untouched.

### 6. Execution environment

Apply the rubric below — infer, then ask, then default:

1. **Infer** each criterion from context: the user's request, the survey, the
   collections (a collection needing system-level deps makes criterion 2 true
   on its own).
2. **Ask** the user about any criterion you cannot infer — one short
   question, not a wizard.
3. **Decide**: any criterion true → scaffold `execution-environment.yml`
   pointing `dependencies.python` at `requirements.txt` and
   `dependencies.galaxy` at `requirements.yml` (confirm the schema against
   the installed ansible-builder's docs), and add `ansible-builder` +
   `ansible-navigator` as dev dependencies. Pin the base image to a
   versioned tag from a maintained EE image repo — a floating `latest`
   undoes the reproducibility the rest of the scaffold buys. All criteria false or
   unresolvable → stop at the EE-ready manifests from step 4.

### 7. Generated README

Write (or append a clearly-bounded section to) the project's `README.md`:

- **Recreate the environment**: `uv sync` on a box with uv; `pip install -r
  requirements.txt` on a stock box that has never heard of uv — the export
  exists precisely for that box.
- **The derived-artifact rule**: `uv.lock` is authoritative;
  `requirements.txt` and `pylock.toml` are regenerated exports — edit
  `pyproject.toml` and re-export instead of touching them.
- **The EE rubric, verbatim**, with the decision this run made and the
  one-file opt-in path if it decided no.

**Done when the README lets someone recreate the environment on a machine
without uv, and states the EE decision.**

## Reference: EE rubric

Scaffold an execution environment when **any one** is true:

1. **The control node is not the user's to mutate** — shared, long-lived, or
   someone else's box.
2. **The control node's platform ≠ the collection's requirements** —
   system-level deps (`libssh`, compilers, a Python the distro won't give
   you).
3. **More than one person or pipeline runs it**, so "works on my machine" has
   actual victims.
4. **The run is scheduled or unattended**, where a drifted host is found by
   an outage rather than a human.

Otherwise emit the manifests in EE-consumable form and stop. A demo has no
retry budget — for interactive, single-run, watched work, the shortest
dependency graph wins.

## Reference: pre-commit roster

From `pre-commit-hooks` (pin current tags at run time):

- `end-of-file-fixer`
- `trailing-whitespace` with `args: [--markdown-linebreak-ext=md]` — the
  two-space markdown line break survives.
- `check-yaml` — add `--allow-multiple-documents` or excludes when the
  project carries multi-document YAML or vault files.
- `check-merge-conflict`
- `check-added-large-files`
- `detect-private-key`
- `mixed-line-ending`

Plus, from their own repos: `ansible-lint`, `yamllint`, and (per step 1)
`ruff` (`ruff-pre-commit`, check + format).
